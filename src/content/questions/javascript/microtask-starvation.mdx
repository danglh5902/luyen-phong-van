## Ví dụ

<Runnable client:visible lang="js" code={`let n = 0;
function loop() {
  if (++n < 1000) Promise.resolve().then(loop); // microtask tự nối tiếp
}
setTimeout(() => console.log("timeout chạy sau, n =", n), 0);
loop();
console.log("sync xong");`} />

Timer có hạn 0ms vẫn phải chờ 1000 microtask xong. Nếu điều kiện dừng không bao giờ đúng, vòng lặp là vô hạn và tab đóng băng, vì microtask queue không bao giờ cạn.

## So với macrotask

- Sau mỗi macrotask, engine drain toàn bộ microtask, rồi mới có thể render và lấy macrotask tiếp theo.
- Đệ quy bằng `setTimeout(loop)` thì ổn: giữa các vòng trình duyệt vẫn render và xử lý input.
- `queueMicrotask` và `Promise.then` cùng queue; `await` trên promise đã resolve cũng là microtask.

## Cách tránh

- Chia việc nặng thành các lô nhỏ, nhường quyền giữa các lô bằng macrotask (`setTimeout`, `MessageChannel`) hoặc `scheduler.yield()` ở trình duyệt hỗ trợ; Node dùng `setImmediate`.
- Với tác vụ CPU thật sự nặng, chuyển sang Web Worker/`worker_threads`.
- `requestIdleCallback` cho việc không gấp.

<Callout type="pitfall">
Vòng `while` đồng bộ cũng chặn event loop như vậy; đừng nghĩ `async` biến code CPU-bound thành không chặn. Chỉ I/O mới thật sự bất đồng bộ.
</Callout>

<Callout type="followup">
Trong Node.js, `process.nextTick` có thể gây starvation I/O theo cách tương tự (ưu tiên cao hơn cả microtask của Promise).
</Callout>
